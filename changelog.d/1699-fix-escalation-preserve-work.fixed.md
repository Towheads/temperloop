- **`/fix`'s Step 4a escalation no longer destroys the escalated worker's committed work when the operator answers inline** (temperloop#1699). That branch said only "record the answer and re-run the drive from Step 2" — and the re-drive reaches `worktree.sh create`, whose unconditional `clear_path` force-removes the worktree **and `git branch -D`s the local `build/<slug>` branch. A worker that had finished, committed, and then been blocked pre-push by a reviewer therefore had its commits deleted and its work re-derived from `origin/<default>`. The branch now probes the escalated worktree (`pr.sh recover-probe`), commits any uncommitted edits, pushes `build/<slug>` to origin as a **preservation ref** — the one place `clear_path` cannot reach, since it operates on the local repo — and rides a `git fetch origin build/<slug>` + `git merge FETCH_HEAD` restore instruction into the re-drive's item `notes:` so the second worker builds on the reviewed work instead of rebuilding it. Every git-level failure in that branch names its disposition: a `recover-probe` that exits nonzero or emits non-JSON (its `resolve_worktree` `die`s, `pr.sh:102-109` — distinct from the fail-soft `RECOVER_NONE` JSON), a nonzero `commit`, and a `PUSH_REJECTED` each **stop** the run and take the **preservation-failure hold** — a named disposition, spelled out once above both branches and deliberately NOT the word "park", which in the very same branch denotes the formal five-step sequence that releases the claim and runs `worktree.sh remove`. The hold is exactly four actions: post a comment naming the git failure, keep the claim held, touch neither the worktree nor `build/<slug>` (they are the only copy), record `held` and stop. In the park branch the failure fires at its own step 1, so steps 2–6 never run at all — stated explicitly rather than left to inference. The commit guard matters because a failed commit leaves `HEAD` at `origin/<default>`, so the following push would send a ref identical to the base and report a healthy `PUSHED` while the edits it exists to protect were never captured; the spec names the mechanical tell (a re-probe still showing `dirty_files > 0`). Field names are the ones `pr.sh` actually emits — `.commits_ahead`, `.dirty`, `.dirty_files` (`pr.sh:442`, header `pr.sh:70`); `.ahead` is the shell variable only and would read `null`. Mechanism field-proven on foundation#1791/#1792.
- **The restore instruction no longer specifies `--ff-only`, and no longer claims the fast-forward "always applies"** (temperloop#1699). It did, on the reasoning that `worktree.sh create` branches off `origin/<default>` and the preserved commit descends from that same base — which holds only while `origin/<default>` stands still, and an escalation's question can sit open indefinitely while unrelated work merges. **Observed, not hypothetical: it fired during this issue's own development.** The preserved tip `26cbdf4` was cut from base `30f7143`, `origin/main` had advanced to `f0c14fd`, and `git merge-base --is-ancestor f0c14fd 26cbdf4` returned FALSE — the `--ff-only` merge was impossible. The work survived only because the worker handed that prose quietly deviated from it and merged plainly (`42b5e39`, two parents), which is precisely the unbacked-prose failure this change exists to close. The instruction is now a plain `git merge`, the guarantee is stated at its real strength (the two commits **share history**, so a merge base exists and the merge is well-defined — not that it fast-forwards, not that it applies cleanly), a **merge commit is named as the correct expected outcome**, and a **CONFLICTING restore merge stops the worker**: leave the conflict un-resolved, return `blocked`/`failed` naming the conflicting paths and both SHAs, never resolve blindly and never rebuild from the base — that last would silently drop the preserved commit, re-creating the original bug one layer down. The preserved ref is safe across such a stop because Step 6 keeps it on every non-merged/non-resolved disposition.
- **Step 6's deletion of that preservation ref is now GATED on a mechanical check that the preserved commit actually landed**, not on the disposition alone (temperloop#1699). The restore half is free-text prose in the re-drive's `notes:`, and nothing verified the second worker obeyed it — so a worker that silently dropped the instruction still produced a green, merged PR, and Step 6 then deleted the sole surviving copy of the reviewed commit: silent and self-cleaning, strictly worse than the deterministic loss it replaced. The step now fetches `build/<slug>` and the default branch and runs `git merge-base --is-ancestor <preserved-sha> FETCH_HEAD`. TRUE deletes the ref as before; **FALSE — or a check that cannot run at all** (missing operand, failed fetch, or a `resolved (verdict)` disposition with no merged tip) — **KEEPS the ref and reports the discrepancy loudly**, naming the ref, the SHA and the PR. Never advisory, never silent-on-failure. `<preserved-sha>` is the `.sha` from `pr.sh push`'s `PUSHED` payload, carried in the run's own state beside `pushed_sha`/`<pr>` and re-readable via `git ls-remote` — no state file, no new setting. The gate sits at Step 6 because that is the irreversible step; an acceptance assertion inside the re-drive would run inside the very worker whose compliance is in doubt. Step 6 now probes for the ref **unconditionally** (`git ls-remote --exit-code origin refs/heads/build/<slug>`) at a merged/resolved disposition rather than only when *this* run pushed it — otherwise the genuinely common cross-session case (escalate and park in one session, resolve cleanly in another, pushing nothing) would never look for the ref and the documented cleanup would be narrative rather than instruction. Broadening is safe because the ancestry gate, not the probe, is what protects the ref.
- **The escalation park branch is renumbered so preservation comes first** (temperloop#1699). It read 1→5 but its step 4 retroactively told the executor to run the preservation push "before step 2" — so an executor following the emitted order reached `worktree.sh remove` (which deletes `build/<slug>` and its commits) having never been told to preserve anything, and step 2's park comment could not name a ref that had not been pushed yet. Preservation is now step 1, the park comment (now step 3) names the pushed ref and its SHA, and no step instructs an action belonging earlier in the sequence.
- **The same spec's `clear_path` warning understated the loss.** It named only the escalated worker's "uncommitted edits"; `clear_path` deletes the branch too, so a reader who had committed reasonably concluded they were safe. The warning is now stated once, above both dispositions, and says plainly that committing is not protection and that no ref in the same repo — tag, stash, or second branch — survives either.
