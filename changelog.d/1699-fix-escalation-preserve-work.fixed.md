- **`/fix`'s Step 4a escalation no longer destroys the escalated worker's committed work when the operator answers inline** (temperloop#1699). That branch said only "record the answer and re-run the drive from Step 2" — and the re-drive reaches `worktree.sh create`, whose unconditional `clear_path` force-removes the worktree **and `git branch -D`s the local `build/<slug>` branch. A worker that had finished, committed, and then been blocked pre-push by a reviewer therefore had its commits deleted and its work re-derived from `origin/<default>`. The branch now probes the escalated worktree (`pr.sh recover-probe`), commits any uncommitted edits, pushes `build/<slug>` to origin as a **preservation ref** — the one place `clear_path` cannot reach, since it operates on the local repo — and rides a `git fetch` + `git merge --ff-only FETCH_HEAD` restore instruction into the re-drive's item `notes:` so the second worker builds on the reviewed work instead of rebuilding it. A `PUSH_REJECTED` stops the re-drive rather than proceeding unpreserved. Step 6 owns the ref's lifecycle: deleted at a merged/resolved disposition, deliberately kept at a parked one (where it is the only surviving copy) for the next `/fix` run on the issue to delete. Mechanism field-proven on foundation#1791/#1792.
- **The same spec's `clear_path` warning understated the loss.** It named only the escalated worker's "uncommitted edits"; `clear_path` deletes the branch too, so a reader who had committed reasonably concluded they were safe. The warning is now stated once, above both dispositions, and says plainly that committing is not protection and that no ref in the same repo — tag, stash, or second branch — survives either.
